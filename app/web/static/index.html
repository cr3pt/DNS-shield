Local anomaly detection

      

        A background check over your own query log, entirely local - no cloud service, no ML,
        just simple per-client thresholds re-checked on a timer. Flags things like a client
        suddenly hammering many blocked domains (compromised app/device), a burst of unusually
        many distinct domains in a short window (typical of DGA malware cycling through
        candidate C2 domains), or an unusually high share of a client's queries being blocked.
        Off by default; enabling it costs nothing beyond the periodic query, and never changes
        how any query is answered - it only ever reads the log and writes an alert here.
      

      

        

          
          
        

        

          

          

          

          

          

          

          

        

        

          A distinct-domain burst only fires if a good share of those domains also look
          randomly generated (Shannon entropy of the domain's own label, e.g.
          "kq7xzpqm3f.info") rather than real words - this is what keeps it from firing on
          ordinary high-cardinality traffic like a page pulling in thirty different real
          ad/tracker vendor domains, which isn't actually suspicious.
        

        

          

          

          

        

        

          DNS tunneling abuses DNS as a covert data channel by encoding data into a long
          stream of distinct, near-random subdomains of one domain (e.g.
          k3f9a...92mz.tunnel.example.com, one unique subdomain per query). This
          fires when a client queries many distinct subdomains of the same domain in
          a window and most of them look like encoded data (long + high entropy) rather than a
          real site's normal handful of subdomains.

Regex denylist experimental

      

        Blocks any query name matching one of these Python regular expressions - e.g.
        ^ads?[0-9]*\. catches ad/ad1/ads2 subdomains across every domain at once,
        something a plain domain/subdomain denylist entry above can't express. Off by default -
        toggle "Enable regex denylist" in Settings -> DNS - since every enabled pattern here is
        checked against every single query - keep the list short. Patterns are compiled once
        and cached in memory, not recompiled per query, but matching itself is still real CPU
        work per query - this is meant for a handful of hand-picked rules, not a full list.
      

      

        
        
      

      

    


    

      
Blocked destination IPs

      

        Blocks a query the moment its answer resolves to one of these IPs/CIDRs, or one from a
        subscribed list below - even for a domain on the allowlist above. Catches a trusted
        domain that's been compromised or rebound to point at a known-bad address; the domain
        allowlist still governs everything else about that domain.

Typosquat protection

      

        Flags a query as a probable typosquat when it's a close spelling variant (e.g.
        paypa1.com, faceb00k.com) or has a protected brand name
        embedded in a longer domain (e.g. paypal-security-check.com) - never an
        exact match or a real subdomain of the protected domain itself. Always raises an alert
        (Anomalies tab, with a notification if configured); Settings -> DNS also has an "On a
        match" choice for what happens to the query itself - resolve it normally (default),
        redirect to the real brand's own address, or redirect to an address you specify.

Blocked clients (no communication allowed)

      

        Every query from these IPs/CIDRs is blocked, for every domain - stronger than a domain
        denylist entry, and takes priority over client groups below. Usually populated via the
        "Block host" button next to a client's address in Logs, Stats, or the Enrich popup;
        add one by hand here too if you'd rather. Also accepts mac:AA:BB:CC:DD:EE:FF
        (matched against the router's ARP table - only populated with real LAN entries when
        DNS-shield runs on the host network) and host:name (matched against the
        resolved client hostname, requires client name resolution enabled in DNS settings).
      

      

        
        
      

      

    


    

      
Client groups

      

        Per-client overrides. First matching group wins; unmatched clients get the global policy
        above. Match patterns accept an IP/CIDR, mac:AA:BB:CC:DD:EE:FF, or
        host:name (wildcards like host:*.kids match a hostname suffix).
